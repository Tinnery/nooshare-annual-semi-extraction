## rustfs-combo 并行化根因诊断 (22:20-22:40)

用户要求「认真分析如何改造为多进程并行」+ 顶尖专家/原始数据/客观标准/重写需求四段式。新增两个可复现诊断脚本：`scripts/bench_rustfs_combo.py`（5 阶段剖析）、`scripts/bench_extract_parallel.py`（thread vs process 对照）。均未改生产代码。

**实测结论（推翻「改多进程就能加速」的前提）**：
- `list_objects` 全量 113,528 对象 / 114 次分页 = 24s 固定开销。
- 串行下载（每次新建 TLS 连接）23.5 f/s；ThreadPool 4/8/16/32 线程一律 43 f/s 封顶（1.8x 即饱和）；keep-alive 单连接串行 39.7 f/s（1.7x，重连 1 次）→ **瓶颈是每请求 TLS 握手 + 服务端单连接能力，不是并发度，更不是 GIL**。加进程无用。
- `extract()` 真实成本 23.5ms/文件（中位文件 399KB、真实分布 500 文件实测），全量纯 CPU ≈ 44.5 分钟，占比 31.7%（下载 68.3%）。Amdahl 上限：即便 16 进程把 CPU 归零也只有 **1.42x**。注意：循环同一文件 1000 次只得 2.2ms（热缓存+单一短报告下界），差 10 倍，基准必须用真实文件分布。
- thread-4/8/16 抽 extract 仅 1.12~1.19x（GIL），process-4/8 = 2.98x/3.40x → **多进程只对 CPU 抽取段有效**。
- 本地已缓存 36,899（2021-2024 交付表口径），RustFS 有 113,528（含 2003 起历史年份），pro 主机无缓存。走本地磁盘单进程 42 f/s → 36,899 需 14.6 分钟；故「消除网络」才是数量级杠杆。

**方法论教训**：首次测 extract 用假文件名 `_bench_combo.md`，`slot_key_from_path` 返回 None 使 `extract` 早退，得出 0.00s / CPU 0% 的假数据；且循环同一文件 1000 次受缓存影响（2.2ms）与真实分布（23.8ms）差 10 倍。**基准必须用真实文件名 + 真实文件分布**，否则反过来误导并行化方向。

**顶层判断**：I/O 段用连接池 + 线程 + 缓存/增量，CPU 段才用 ProcessPool；两段解耦。仅当先消除网络下载后，多进程才有意义（本地 14.6 分钟 → 约 4 分钟）。

**⚠️ 上述诊断被用户推翻，结论作废（22:50-23:10）**：诊断全在**本地 Windows 跨网络**测的，而任务跑在 **pro 主机（192.168.31.233）**，RustFS 也在同一台机器。用户指出两点：① 8 个进程并发访问 RustFS，网络等待会重叠，不是 Amdahl 串行段，"1.42x 上限"物理上不成立；② 可直连 localhost 明文端口绕过 TLS。两点均经实测证实：`s3.rustfs.pro.neuralj.com` → 192.168.31.233，RustFS 监听 9000(http)/9001，443 为 TLS 反代。http 直连单请求 0.8ms / 串行 1077 f/s，比本地 Windows 走 TLS 的 42ms / 23.5 f/s 快约 50 倍。**教训：性能诊断必须在真实运行环境测，否则数据再漂亮也是错的。**

**已落地（commit 2553be5，pro 主机代码 sha256 已核对一致）**：
1. `rustfs.py`：`RUSTFS_ENDPOINT` 环境变量可配，http 用 `HTTPConnection` 走 9000 明文；新增 `client.endpoint` 属性；`_new_connection()` 统一按 scheme 建连。本机运行务必用 `--endpoint http://127.0.0.1:9000`。
